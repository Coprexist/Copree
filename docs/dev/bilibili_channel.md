# B 站通道插件（bilibili）

> 状态：**已实现**（2026-10-31）
> 位置：`backend/plugins/bilibili/`（内置插件，同时以 verified 条目进社区索引）
> 参考实现：AstrBot `astrbot_plugin_bilibili`（动态订阅推送）、`bili-cli`/`bili-agent`（Agent 优先的 CLI）、DSH 的 bilibili 插件（链接解析）

## 1. 形态：为什么放在通道侧

B 站的登录态属于**某个人的 B 站账号**，而 Copree 里"谁在用什么外部账号"这件事由**通道**表达
（QQ 通道就是"一个机器人一个 AI"）。所以：

| | 普通插件（service 单实例） | 通道插件（本插件） |
|---|---|---|
| 配置归属 | 全局一份 | 每个 AI 一份（`instance = agent-<id>`） |
| 凭据 | 插件全局 Cookie | **这个 AI 的** Cookie，加密存在该实例配置里 |
| 谁登录 | 管理员 | **这个 AI 的创建者**自己扫码 |
| 卡片位置 | 能力与扩展 | 这个 AI 的通道页 |

工具按 `agent_id` 取该实例的登录态，所以同一个部署里多个 AI 可以接不同的 B 站账号。

## 2. 扫码登录（没有新增接口）

通道卡片的唯一约定是"插件报状态"（`get_status()` 的 detail）。登录因此做成**状态驱动**：

1. 没有 Cookie → 调 `passport.bilibili.com/x/passport-login/web/qrcode/generate`，把 `url` 放进
   `detail.login.qr_url`，同时带上 `expires_in`
2. 每次取状态顺手 poll 一次（`qrcode/poll`）：等待扫码 / 已扫码待确认 / 成功 / 失效
3. 成功时从响应的 `Set-Cookie` 取 `SESSDATA / bili_jct / DedeUserID`，用
   `plugin_config.set_config(instance=...)` 加密写回，然后调一次 nav 拿昵称
4. 有 Cookie 但 nav 说没登录 → 清空凭据、下次取状态重新出码

**为什么 `sessdata` 不是 required**：通道保存要求必填项齐全，若登录前就必填，
"没登录 → 不能保存 → 没有实例 → 出不了二维码"会死锁。

二维码会话按实例缓存（`_qr_sessions`）：反复刷新卡片不会换码——B 站会把旧码判失效。
登录态校验有 120 秒缓存（`_nav_cache`），卡片被反复拉取时不会把 nav 打爆。

## 3. 状态与工具

| 工具 | 登录 | 说明 |
|---|---|---|
| `bili_account` | — | 这个 AI 的登录态/昵称/UID |
| `bili_video` / `bili_hot` / `bili_user` / `bili_live` | 否 | 视频详情、热门、粉丝数、直播状态 |
| `bili_search_user` | 否 | 按昵称搜人（昵称 → mid）；重名/高仿靠粉丝数与签名分辨 |
| `bili_search_video` | 否 | 按关键词搜视频；`order` 换排序（综合 / 最新 / 播放 / 弹幕 / 收藏 / 评论） |
| `bili_user_videos` | **是** | 列 UP 主投稿（`x/space/wbi/arc/search`，WBI 签名） |
| `bili_like` / `bili_comment` | **是** | 视频点赞/取消；评论（发 / 回 / 赞 / 置顶 / 删，要 `bili_jct` 当 CSRF） |
| `bili_dm` | **是** | 私信：`list` 列会话（谁、未读几条、最后一句）/ `read` 读最近几条 / `send` 真发一条（`web_im`，见 §3.4） |
| `bili_inbox` | **是** | 消息中心：回复我的 / @我的 / 收到的赞 / 未读私信。不带参数只报没念过的；带 `days`/`since`/`until` 查本地流水并按帖子/天/人聚类（见 §3.5） |
| `bili_comments` | 否 | 读视频评论与楼中楼（`sort=hot` 热度 / `time` 最新在前） |
| `bili_danmaku` | 否 | 读视频弹幕（老接口 `x/v1/dm/list.so`，deflate XML；可只看某时间点前后） |
| `bili_subtitle` | 否 | 读视频的语音识别稿（人说了什么，见 §3.2） |
| `bili_shot` | 否 | 取某几秒的画面（B 站抽好的缩略帧，见 §3.3） |
| `bili_dynamics` | **是** | UP 主最新动态 |
| `bili_subscribe` | 否（推送要登录） | 订阅管理（按实例 + 群） |

未登录时 `bili_dynamics` 直接抛 `BiliError("这个 AI 还没有登录 B 站…")`，不静默降级。

搜索走站点的 `x/web-interface/search/type`（`search_type=bili_user` / `video`），**不需要登录、也不需要
自己算 WBI 签名**；返回里命中的关键词带 `<em class="keyword">` 高亮，`_plain()` 负责脱标签。
搜视频的 `order` 直接透传给接口：`totalrank` 综合 / `pubdate` 最新 / `click` 播放 / `dm` 弹幕 /
`stow` 收藏 / `scores` 评论（实测六个都生效）；没有"正序"，时间类排序一律最新在前。
写操作（点赞/评论）走 `_post()`：表单提交到 `api.bilibili.com`，带 `Origin`/`Referer`（少了会 -403），
CSRF 用登录时存下的 `bili_jct`；点赞接口的 `like` 参数口径是 **1=点赞、2=取消**（传 0 会被判 -400），
取消时若本来没赞过，B 站回 `65004`，`BiliLike` 把它当成"现在没赞"的成功结果。
评论要先 `x/web-interface/view` 拿 `aid` 再 `x/v2/reply/add`（`oid=aid, type=1`）；删自己的评论用
`x/v2/reply/del`（`type=1, oid, rpid, csrf`，`12022` = 已经删了，按成功处理）；给评论点赞/取消用
`x/v2/reply/action`（`type=1, oid, rpid, action=1|0, csrf`，实测自己的评论和别人的一样能赞）。

读评论的排序是 `x/v2/reply/wbi/main` 的 `mode`：**2 = 按时间（最新在前）、3 = 按热度**（2026-11-02 实测，
写成别的码会被接口当默认处理）。接口没有"最早在前"这个排序，深翻页（`pn` 顶到末页）直接回空列表，
所以想要最早那几条只能顺着时间一页页翻——工具里因此只给 `hot` / `time` 两种口径。

发评论**不等它公开**：提交成功就返回「发布中」，同时写一行 `plugin_bilibili__pending`（迁移 `0003`）。
B 站刚收到评论时先标成隐藏/折叠、几秒到几分钟才放出来，等下去只会把 AI 的整轮对话卡住。

每个实例一个追认任务（`bilibili-pending-<instance>`，30 秒一轮），用**登录态**读评论列表
（`x/v2/reply/wbi/main`，按时间倒序最多 3 页）看 B 站挂在评论对象上的状态字段：

| 字段 | 正常 | 异常 |
|---|---|---|
| `state` | `0` | `17` = 被 B 站隐藏（只有作者自己看得到，别人看不到） |
| `invisible` | `false` | `true` = 不可见 |
| `folder.is_folded` | `false` | `true` = 收在折叠栏里（仍然公开，点开就能看到；过一阵会自己恢复） |

落定后往这个 AI 的会话账本投一条通知（`api.report_notice`，`drop_on_unlock`，**不进群聊**），
`ref=bili_comment:<rpid>:<公开|隐藏|未确认>`：

- 公开 → 「你刚发的评论已经公开了」；
- 刚发出的一段时间 B 站本来就标成隐藏，这之前不下结论（`PENDING_SETTLE_SECONDS` = 90 秒）；
- 90 秒后仍是隐藏，或半小时还没落定 → 告诉 AI 没公开（可能被折叠或隐藏）。

`visible` 只看 `state`/`invisible`：折叠不等于看不到（2026-11-01 实测：刚发出时 `is_folded=true`，
几分钟后再看已经是 `false`，期间一直公开），所以折叠只作为附加信息，不参与可见性判断。
不用"匿名接口能不能查到"当标准：匿名列表虽然还能用（2026-11-01 实测 `x/v2/reply` 200、55 条），
但匿名接口的返回随策略变，而评论对象上的状态字段是权威信号。
删评论会同时删掉它的待确认行：已经删掉的东西不必再追认可见性。
写请求必须长得像网页端发出的：`Referer` 用视频页、查询带 `web_location=1315875&plat=1`、
正文带 `dm_img_list / dm_img_str / dm_cover_img_str / dm_img_inter` 四个设备指纹字段，Cookie 里除登录态还要
`_uuid / b_nut / b_lsid / buvid_fp`（进程内固定）。**缺这些时接口照样回 `code=0`，但评论会被隐藏成仅作者可见**——
2026-11-01 实测：只带登录 Cookie 发的四条（含最短最朴素的一句）全部 `state=17`；补齐上述形状后同一账号同一内容
立刻 `state=0` 公开。所以这既不是账号问题，也不是文案问题。

能不能替创建者说话由创建者决定：插件设置里的 `allow_interact`（默认关）。勾上后它才能用这个账号点赞、
评论、发私信；关闭时只读，写工具会明确报「创建者还没允许这个 AI 互动」。
搜索接口是限流的：短时间连打会回 HTTP 412（与登录态无关），`_data_of()` 把 412 单独翻译成"隔几秒再试"；
请求默认附上 `finger/spi` 发放的 `buvid3/buvid4` 设备指纹（缓存 30 分钟），实测连打三次不再 412。
指纹只治限流、与评论可见性无关（2026-11-01 A/B：写请求带与不带 buvid，评论都是 `state=0`）。

## 3.1 状态帧（`bilibili_browse`）

配置项 `frame_enabled`（默认开）勾着时，实例启动 / 卡片刷新会调 `_ensure_browse_frame`，用平台的
插件帧接口（`api.enter_frame(..., switch=False)`）预建一条**沉睡**帧：`type=bilibili_browse`、
`context_ref=bilibili:<agent_id>`、工具白名单取自 `plugin.json` 的 `frames` 段（B 站那套 + 状态/记忆工具，
不含 Copree 的群聊/私信收发——B 站站内的私信收发是 `bili_dm`）。名单里留了 `end_turn`：
  「不想刷了、这一轮就此打住」得有出口，否则他只能空转到轮次用完，或者被迫 `finish_frame` 把帧收掉
  （2026-11-06 就是因为缺它，连试三个被拒的工具烧掉七轮）。名单里还留着 `compress_context`：
  这一帧一轮能跑 50 次调用，长起来要能自己提前压（平台的自动压缩与它无关，照样生效）。沉睡帧只进存储，
  不改变 AI 当前在哪；
要不要进由它自己决定——`list_states` 看到 id，
用平台的 `enter_state` 进来，出来用 `pop_state`。

进帧时插件会被平台问一次（`on_frame_enter` 钩子），它趁这一次把 B 站站内的新消息念进帧的账本：
**回复我的**（`x/msgfeed/reply`）、**@我的**（`x/msgfeed/at`）、**收到的赞**（`x/msgfeed/like`）、
**未读私信**（`session_svr/get_sessions` + `svr_sync/fetch_session_msgs`，发送者名字走 `account/v1/user/cards`）。
同一套读取也给工具 `bili_inbox` 用（见 §3.5），逻辑只有一份。要点：

- 是**注入不是唤醒**：这些消息不会让平台开新轮，回不回由 AI 自己看上下文决定；
- **不动 B 站的未读标记**（那是用户手机上的红点），念到哪一条记在 `plugin_bilibili__inbox`
  （`agent_id / kind / cursor`，kind = reply / at / like / im:<talker_id>），同一条只念一次；
- **先写进账本，再推进游标**：未读变已读的全部含义就是"他之后还能翻到"。账本走平台的一步入口
  `api.notify_agent(...)`（返回 True 才推游标）。一轮最多记
  `_INBOX_MAX_LINES=12` 行，记不下的不推进游标、下次接着念——宁可多念一遍，不能出现
  "标成已读却读不到"；
- **看见的每一条都存一份**（流水表 `plugin_bilibili__feed`，插件迁移 `0005`）：B 站的消息接口
  没有按时间取的能力，"上周谁回了我"只能问自己。`ts` 存的是**消息自己的时间**
  （`reply_time` / `like_time` / 私信时间），不是我们读到它的时间——补扫到三年前的回复
  不该被算成"最近七天"；`(instance, kind, item_key)` 唯一（回复/@ 用 rpid、赞用
  `<id>:<like_time>`、私信用 `<talker>:<msg_seqno>`），重复扫到不新增，但**渲染字段按这次扫描
  覆盖**：口径改了，下次扫到就跟着改，不用回填；
- 赞的形状和别的不一样：`x/msgfeed/like` 分 `latest`（B 站认的"新赞"，`last_view_at` 一更新就清空）
  和 `total`（按被赞目标聚合的历史：一条里 `users` 是一串人、`counts` 是累计赞数）。两条都读，
  游标记 `like_time` 而不是 id——同一个目标被再赞一次 id 不变，按 id 会漏；
- 系统通知（登录提醒等，带 `notify_code`）只扫不念，游标照样越过它；
- 额度与建议时长也在进帧那一刻念一遍：`frame_round_limit` / `frame_hour_limit` / `frame_day_limit` /
  `frame_session_minutes`（建议单次多久，只是建议），见 `docs/plugin-dev/plugin-frames.md` §5.1。

帧归 AI：`list_states` 能看到、`pop_state` / `close_state` 能收。插件侧只做代建，靠的是平台在服务
生命周期里注入的插件上下文（`api.plugin_context`）。

## 3.2 读视频里人说的话（`bili_subtitle`）

稿件列表在播放器配置里（`x/player/v2` 的 `data.subtitle.subtitles`，每项带 `lan` / `subtitle_url`），
正文在 `aisubtitle.hdslb.com`——**顶层直接是 `body`，没有 `code/data` 信封**，所以走 `_raw_get`，
过 `_data_of` 会被当成反爬页面。一条稿子是一串 `{from, to, content}`。

- 挑哪条：优先 `ai-zh`（整片人说了什么都在里面）；没有才比人工稿字数——人工稿常常只翻歌曲和几句标题，
  同一条视频里 `zh-Hans` 实测只有 `ai-zh` 的零头。少数视频有 8 条语种轨（`ai-zh/ai-en/ai-ja/…`）。
- **会串台**：B 站偶尔把**别人的**稿子挂在这条视频的记录下面（实测 70 分钟的视频拿到过 53 秒的娱乐新闻稿、
  火锅探店稿、换车轮的 Vlog；同一条视频连问几次，返回的稿子会在"对的"和"别人的"之间跳）。好消息是
  ai 稿地址里内嵌了身份：`bfs/ai_subtitle/prod/<aid><cid><hash>`，所以 `_ai_url_of()` 能当场认出串台，
  认出来就丢掉重问（`_SUB_TRIES=4`）；全都不对时**如实回"拿不到"**，绝不把别人的话当成这条视频的内容。
- 一次只回一段：上限 `_SUB_CHARS=2000` 字，尾巴上带"后面还有 N 分钟、接着读给 from=…"；
  `from` / `to` 收秒数，也收 `mm:ss`（模型会把上一条的 `范围` 原样填回来）。
- 稿子按分 P 缓存一小时（`_sub_cache`）：同一段视频要分几次读，不该每读一段都重新问一遍 B 站；
  只有覆盖到 90% 以上时长的稿子才缓存，半截稿不缓存（否则等于把它钉住一小时）。
- 覆盖不到全片时结果里带 `注意`：B 站可能还没生成完，也可能后面只有画面没人说话——两种情况都不猜。

## 3.3 看某一秒的画面（\`bili_shot\`）

B 站自己把视频按等间隔抽成了缩略图雪碧图（网页播放器拿来给进度条做悬停预览），所以取画面
既不用下载视频，也不用 ffmpeg：\`x/player/videoshot\` 回一张或多张 4800×2700 的拼图，
外加一份时间轴 \`index\`。布局：每张 10 行 × 10 列、每格 480×270、行优先；\`index[n]\` 落在
第 \`n // 100\` 张拼图的第 \`n % 100\` 格（实测 70 分钟的视频 6 张拼图 / 510 个时间点，
最后一张只用 10 格；空白的格子是视频首尾的黑帧，不是没填满）。

- 给了 \`at\`（最多两个时间点）：取**那个时刻前后各一格**——单帧可能正好落在转场或黑帧上，
  两帧连看才看得出动作；时刻正好落在格子上就再往后多看一格。
- 不给 \`at\`：取开头两格，并跳过时间重复的格子（头两格有时都标 0 秒，取两个 0 秒等于只有一张）。
- 时间超出片长直接报错，不悄悄给最后一帧（越界多半是拿了别的视频的时间轴）。
- 每格用 Pillow 裁成 480×270 JPEG（约 20–25 KB）；拼图原图按 URL 缓存一小时，
  同一段视频连着看几处不必重复下载。

**图片怎么到模型眼前**：工具结果里的 \`images\` 由执行器摘出来（\`_take_tool_images\`），
工具消息只留文本；紧跟着注入一条 \`user\` 消息（\`【工具附图】… 第1张 00:20、第2张 00:30\`）
加一条 system 便签（"工具刚返回的画面含 N 张图片，你可以直接查看"）。原因是多数供应商的
\`tool\` 角色只收文本，图片塞进工具消息的 JSON 还会连带污染对话日志。

- 落库前 \`strip_image_bytes\` 把图片字节换成 \`[图片]\` 占位：日志是整份请求体的快照，
  几 MB base64 会把账本撑爆，回看时也没人读那些字节。
- 纯文本模型收到图片会被供应商 400，由 \`strip_image_parts\` 剥掉图片重试——这条降级路径
  用户附图时早就有，工具附图走同一套。
- 帧是等间隔抽的（约 5–8 秒一格），所以每张的标签写"实际画面时间"，不是"你要的那一秒"；
  \`frames[i]\` 与 \`images[i]\` 一一对应，顺序即对应关系，模型据文字认图。

## 3.4 私信（`bili_dm`）

收件箱（§3.1 的进帧投递与 `bili_inbox`）只负责"让人知道自己有私信"，**回不了话**。真正读写的入口是这个工具：

- `list`：最近的私信会话（按 `session_ts` 倒序），每个给 uid、昵称、未读数、最后一句、时间。
  最后一句带**方向**（`{"谁": "我" | "对方", "text": …}`）：会话的"最后一条"经常是它自己发的，
  不标方向会读成对方说了这句话（2026-11-03 线上就发生过：它把创建者自己发的那句当成
  对方来找它交流）。取的是"最近聊过的人"，不是 B 站的未读红点——红点归用户手机。
- `read`：某个会话最近几条，按 `sender_uid` 标方向（我 / 对方），没有正文的（图片、卡片、系统提示）跳过。
- `send`：`web_im/v1/web_im/send_msg`，表单是 `msg[sender_uid]` / `msg[receiver_id]` /
  `msg[msg_type]=1` / `msg[content]` 这一组扁平字段，CSRF 仍是 `bili_jct`，`dev_id` 用浏览器身份里的
  `_uuid`（与 Cookie 同源，进程内固定）。走 `api.vc.bilibili.com`，不是站点的 `api.bilibili.com`。

`who` 认人分三步：纯数字当 UID；否则**先在已有私信会话的昵称里找**（完全一致优先，其次包含）；
都没有才去全站搜人，且只认昵称完全一致的那个。理由是私信发出去收不回——按昵称命中一个陌生人是
不可挽回的错，宁可让它报"找不到，用列表里的昵称或 UID"。

发送前有三道闸：`allow_interact` 没开就抛（与点赞/评论同一道）、不给自己发、正文最多 500 字。

## 3.5 消息中心（`bili_inbox`）

§3.1 那套读取也是工具：AI 想主动问"有没有人赞我、回我"时调它。两种用法共用一条数据链：

- **不带参数 = 同步**：一次调用做三件事——读消息中心、把念到的写进账本、再推进游标
  （顺序见 §3.1），顺手把这一窗里看见的每一条存进流水。数放在头一行：
  `新: "赞 12 · 回复 2（已记进账本，之后还能翻）"`；一次没念完的写成
  `另有 N 条这次没念到，下次叫我会接着念`。没有新的就一句 `没有新的互动`——以前它拿
  "翻评论区没找着自己"去推这种结论（2026-11-06 因此说"没有新回复"，而账本里三条回复正躺着）；
- **带 `days` / `since` / `until` = 查**：只读本地流水，**零网络**，O(区间里的条数)
  （走 `(instance, ts)` 索引，一次最多 `_FEED_CAP=200` 行）。`since`/`until` 收
  `2026-11-01`、`11-01`、`11-01 12:00`；只给日期时终点算到次日 00:00（「到 11-05」得把
  11-05 一整天算进去）；只给 `days` 就是「最近几天」。返回 `区间` + `新` + `聚类`：
  ```
  · BV1z54G6vEMR（回复 9 · 赞 3）
    · 11-04 00:09 回复｜布鲁布鲁桑｜BV1z54G6vEMR#319113399761｜你老大知道你这么消耗他的token吗？
    · 11-06 19:30 赞｜绯想天桃桃子 等 5 人｜BV1z54G6vEMR｜共 12 赞
  ```
  `by` 选口径：`帖子`（默认）/ `天` / `人`。组按最近一条倒序、组内按时间正序——同一个帖子下
  的八条回复摊成八行，模型会当成八件事，聚起来才看得见「这条视频今天热闹了」。私信不是「帖子」，
  按对方聚（`私信 · 某人`）；
- 行是给模型读的，不用 JSON：格式 `类别｜谁｜在哪｜说了什么`，例如
  `回复｜白龙骑士加拉哈德｜BV1ba4g6LEak#319113240673｜[doge]鱼来！鱼来！`。楼中楼把 `root_id`
  跟 BV 号用 `#` 连在一起带上——不带它就接不上话（`bili_comment action=reply` 要 `rpid`）；
  被赞的是评论时 `#` 后面是那条评论的 rpid（同一个人隔几秒赞了同一视频下的两个评论，
  不带就会渲染成一模一样的两行）。「在哪」三级退回：BV 号 → 标题（动态/专栏）→
  `（没挂到具体帖子）`；
- 赞行带 B 站给的 `counts`：`赞｜绯想天桃桃子 等 5 人｜BV1z54G6vEMR｜共 12 赞`。这是**这条一共
  多少赞**，和「新来几个赞」不是一个数——2026-11-07 那个 46 赞就是因为不渲染它，AI 一直看不见；
- `_INBOX_CHARS=100` 截断：12 行约 300 字。

## 3.6 发评论 / 回评论 / 删评论（`bili_comment`）

三个动作共用一次提交，但落点与权限各有各的坑。判断全收在三个函数里
（`_reply_anchor` / `_locate_comment` / `_owner_error`），工具层不再各自判断。

**回评论必须同时给 `root` 和 `parent`**。B 站对"只给 root"这一种缺失**不报错**：`code=0`，
然后把它当成视频下的新评论丢到最顶层。2026-11-21 线上就是它——AI 说自己"回了"，用户看到的
是一堆新评论，被回的人什么都没收到。`_reply_anchor(aid, rpid)` 因此返回**二元组** `(root, parent)`：
`rpid` 是根评论就回自己，是楼中楼就先问 `/x/v2/reply/reply` 拿整栋楼的根。返回二元组而不是
两个函数，是为了让"漏发一个字段"在类型上就写不出来。工具 schema 里也没有 `parent`——
模型只负责说"回哪条"，这套推导不该出现在它的选项里。

**落点对不对只能看 root**。B 站楼中楼只有一层，同一线程下所有回复平铺显示、没有二级嵌套；
所以判断标准是 `root.rpid == 线程根`，`parent` 只影响 @ 谁。

**删评论只有两种人有权限**：评论作者本人、视频作者（删自己视频下的）。删别人的一定 `-403
访问权限不足`——而这句话对模型没有指导性（它可能理解成"账号坏了"再去重试）。所以 `delete`
之前先用 `_owner_error()` 看一眼归属，是别人的就直接回：

> 这条不是你发的（是「江西华龙兄弟」的），B 站只允许删自己的评论，删别人的一定 403。
> 要删自己的，先用 bili_comments 看你在 BV… 下发过哪几条，拿它们的 rpid。

**发出去 ≠ 已公开**：`x/v2/reply/add` 成功后内容先"发布中/隐藏"，几十秒到几分钟才放出来。
所以回复返回的 `rpid` 会记进 `plugin_bilibili__pending`，由每 30 秒一次的 `_check_pending()`
追认（`PENDING_SETTLE_SECONDS=90` 之前不下结论；`PENDING_TTL_SECONDS=1800` 到了还没结论
就算没公开）。落定后通知 AI，**口径按是否需要动手分**：

- 公开成功的**合并成一条**：`刚发的 9 条评论都已公开，不用再管了（BV… 下 5 条、…）`。
  成功没有增量信息、也没有可做的动作，逐条报只会把账本糊满；
- 被隐藏 / 没确认的**逐条报**，带正文摘录与链接——失败每条都不一样，细节才是信息。

追认的定位靠 `_locate_comment(aid, rpid)`：`/x/v2/reply/reply?root=<rpid>` 一次请求就能问清
"它自己就是根（顶层评论，1 个请求定案）"还是"它在某栋楼里（顺带拿到线程根与 `page.count`）"。
楼中楼按时间**正序**排、刚发的那条必然在末尾，所以直接跳最后一页，不从第一页翻起
（2026-11-21 实测：9 条结算只用 10 个请求；改之前每 30 秒打 27 个、还永远找不到）。

## 4. 订阅推送

- 数据：插件自己的表 `plugin_bilibili__subscriptions`（`instance / mid / group_id / name / last_ts`，
  `(instance, mid, group_id)` 唯一），DDL 在 `migrations/0001_init.py`，见 `docs/plugin-dev/plugin-storage.md`
- 每实例一个轮询任务（`start()` 里起，`stop()` 里收），无订阅时空转不请求
- 推送：`send_gm_message(sender_type="ai", sender_id=群里某个 AI 的 user_id, source="world", via="bilibili")`
  - 群里没有 AI → 跳过（不留幽灵消息）
  - `source="world"`：不是"人发的"，不触发群消息钩子，避免自激
- 一个 UP 主一轮最多推 3 条，不补推

## 5. 使用轨迹（插件自己的表）

- 表：`plugin_bilibili__activity`，**只存机器数据**：`action`（工具 id，或 `push` / `login`）、
  `raw`（这次调用实际带的参数 JSON）、`ok`、`duration_ms`、`created_at`
- 动作名（搜用户 / 点赞 / 推送…）与参数名（keyword → 关键词、limit → 条数）都由插件声明三语
  （`_TRAIL_LABELS` / `_TRAIL_ARG_LABELS`），`_trail_recent()` 随 `detail.activity.i18n`
  的 `actions` / `args` 两份字典一起给界面——**翻译不进库**：换语言、改叫法、加工具都不用回填
- 参数项可以带一句「值的格式」（`fmt`，`{}` 占位）：`limit` 渲染成「最多 2 条」而不是
  「条数=2」——**那是 AI 要的条数（上限），不是搜到的条数**；`keyword` 渲染成「「梦月吟希」」。
  没有格式的参数退回「名字=值」，布尔值显示「是 / 否」
- 卡片默认显示「动作名 · 参数」（`搜用户 · 「梦月吟希」 · 最多 5 条`），点「看原文」切成
  「工具 id + 原样 JSON」；字典里没有的名字退回机器名（不猜）
- 每个实例只留最近 500 条（每写 20 条顺手裁一次）
