# 容量准入（同时跑几个回合）

**它解决什么**：一个回合要占一份提示词（几万 token）和一到几条数据库连接。并发以前只在
**群**这一级限（`chat_chain` 每群一个信号量），进程里没有总量——群一多，一起进来的回合就把
连接池和事件循环挤满。挤满之后不报错，而是"所有群一起变慢、状态停在思考中"。2026-11-07
那次 12 小时冻结根因在数据库锁，但**形态**一模一样：一个回合卡住，后面所有人排队。

## 三条边界（设计约束，不是实现细节）

### 1. 阈值不来自观察

上限、下限、压力阈值**全部来自配置**。代码里没有任何"线上大概是多少"的数字。理由很直接：
同一份代码可能跑在"只有一个 AI"的开发机上，也可能跑在十万、百万 AI 的分片集群里，任何从
某套实例统计出来的经验值，对另一套都是错的。

唯一的推导是从**连接池配置**推：`AI_MAX_CONCURRENT_TURNS=0` 时上限取
`pool_size + max_overflow`。那是部署方自己给的硬资源，也是排队真正会落到的位置——把排队
提前到准入层，才有优先级和观测。

### 2. 额度是**本进程**的

| 规模 | 形态 | 这里的表现 |
|---|---|---|
| 1 个 AI | 单进程 | 一次整数加减，不排队、不建对象（`hard=0` 或远大于实际并发） |
| 千级～万级 | 单进程多分片入口 | 总闸把峰值钉住，@/私信优先，普通群聊排队 |
| 10 万 / 100 万 | **多副本 + 分片 + 外部队列** | 每个后端进程各管自己这片额度；跨进程的总额度归部署层（网关、租户配额、Redis 计数） |

第三行是关键：**本模块不假装自己是全局配额。** 它只保证"本进程同时跑几个回合"这一个
不变量。到了需要分片的那天，业务代码不用改——每个副本启动时读自己的额度即可。

### 3. 自适应只在硬上限内收敛，且默认关

`AI_ADAPTIVE_CONCURRENCY=false`（默认）时只采样不动作。打开后是 AIMD（TCP 拥塞控制那套）：

- 没压力 → 每 10 秒试探性 +1；
- 任何一个压力信号越线 → **立刻减半**，然后冷却 60 秒。

它的职责不是猜出"正确值"（我们并不知道），而是部署方给了宽上限时别一次打满。永不越过
`hard`，也永不低于 `floor`。

压力信号三个，都是只读，按顺序判定：

| 顺序 | 信号 | 为什么用它 |
|---|---|---|
| 1 | 排队时长 p95（最近 60 秒，`admission.recent_p95_ms`） | **"用户真的在等"的直接代理**。Netflix Vegas / Envoy Gradient 也是用延迟估队列，而不是看 CPU/内存 |
| 2 | 事件循环调度延迟 p95（`LoopLag`） | 兜底：会被无关的慢操作污染（某个插件出网卡 3 秒），所以不再是主信号 |
| 3 | 连接池 `checked_out / capacity` | 真排队已经发生的地方 |
| 4 | 入口队列深度（`metrics.current_queue_depth`） | 消息进来的速度超过处理速度 |

排队样本**带时间戳**、只算最近 60 秒：十分钟没排队时，旧样本不该被当成"现在还在排队"
（否则会一路缩到下限）。没排队就没有样本，分位为 0——不是"健康"，是"没有这段时间的等待"。

**不用 RSS 当主信号**：Python 的内存还给 OS 很慢，看它会一路加到底（实测 1000 个
`httpx.AsyncClient` 释放后 RSS 几乎不降）。RSS 只适合当最后一道保险。

## 管理员给的内存线（设置页，可选）

上面那套阈值是"技术压力"，但一台机器真正先撞到的往往是内存，而这个镜像可能跑在 2 GB 的
树莓派上、也可能跑在 128 GB 的服务器上。所以**把这条线交给管理员**：

| 设置项 | 含义 |
|---|---|
| 日常内存占用（`memory_daily_target_mb`） | 舒适水位；超过就收紧并发，接近（85%）就停止试探增长 |
| 内存占用上限（`memory_limit_mb`） | 硬线；达到或接近（90%）立刻收紧，与是否开自适应无关 |

- **0 = 不设**：完全忽略内存，走默认算法（延迟 / 池子 / 队列）——这就是"不填也没关系"的保底。
- **口径是"这个服务占多少"**：优先读容器 cgroup 用量（含 chromium、常驻世界等子进程），
  裸机直跑才退回自己进程的 RSS。管理员看 `docker stats` 是多少，这里就该是多少。
- **判定顺序**：管理员的上限 → 管理员的日常线 → 默认三个信号。他写下的线排在前面，
  命中了就收缩，不看冷却、也不等其它信号。
- **一次压力只应对一次**：收缩后进入 60 秒冷却，期间不重复减半（否则超限状态下每 10 秒减半
  一次，一分钟就掉到 1）。持续超限就每冷却周期再收一次，因此从 hard 走到 floor 是分钟级的
  渐进过程，不是瞬间打到底。
- **设得比基础占用量还低**会一路收到 floor，此时记一条 ERROR 明说"上限似乎低于本服务的基础
  占用，请调大或留空"，并停止重复刷日志。
- 服务端校验：两个都设时要求**日常 ≤ 上限**（否则"日常水位"永远高于硬线，调控会一直缩到底）。
- 保存即生效（接口直接推给准入层），之后由 governor 每分钟从库里兜底刷新一次——
  绕过接口直接改库也能在一分钟内跟上。

## 用法

一个入口，只给"会并发派发的回合"：

```python
async with admission.slot(capacity.HIGH):   # 或 capacity.NORMAL
    ...一个回合...
```

接入点只有两处（都是 `asyncio.create_task` 派发、天然并发的地方）：

- 群聊回复：`_trigger_one`（在群信号量**之内**——别占着全进程的名额去等某一个群）；
- 群助手：`_admitted(HIGH, ...)`。

**私信与闹钟不接**：它们在单消费者的 `ai_response_worker` 里是直接 `await` 的，天然最多
一个回合，再套一道闸只会让它们互相等。哪天把私信改成并发派发，再一起接进来。

优先级只有两档：`high`（@我 / 全体 / 群助手：有人在等）、`normal`（群里路过的一句）。
放行顺序先 high 后 normal，同类 FIFO——不做这层，上限越小，普通消息越会把 @ 挤在后面。

## 配置

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `AI_MAX_CONCURRENT_TURNS` | 0 | 本进程同时运行的回合上限；**0 = 跟随连接池容量**，负数 = 不限 |
| `AI_ADAPTIVE_CONCURRENCY` | false | 是否让目标值在 `[floor, hard]` 间自动收敛 |
| `AI_ADAPTIVE_FLOOR` | 1 | 自适应下限（再忙也不低于它，否则会饿死） |
| `AI_PRESSURE_QUEUE_LAG_MS` | 2000 | 排队时长（最近 60 秒 p95）超过它就收缩；调大等于关掉这条 |
| `AI_PRESSURE_LOOP_LAG_MS` | 250 | 事件循环延迟超过它就收缩（兜底信号） |
| `AI_PRESSURE_POOL_RATIO` | 0.9 | 连接池占用超过它就收缩 |
| `AI_PRESSURE_QUEUE_RATIO` | 0.8 | 入口队列超过它（相对 500 的容量）就收缩 |

另外两项不在环境变量里，而是管理台「系统设置 → 容量与内存策略」（存进 `system_settings`，
迁移 `0108` 加的两列）：
`memory_daily_target_mb`（日常内存占用）与 `memory_limit_mb`（内存上限），单位 MB，0 = 不设；
它们存进 `system_settings`，保存即生效，不需要重启。

改完重启生效：上限刻意不做热更新——一个正在收缩的闸，突然被人调大，观测和因果都会乱。

`admission.waiting_ms` 是**最近 60 秒**的排队分位，`last_wait_ms` 是最近一次排队的时长——
两个都看，才不会把"很久以前排过一次长队"读成"现在还在排"。

`memory.source` 是读数来源（`cgroup2` / `cgroup1` / `rss`）——排查"管理员看到的数和面板对不上"
时先看这一格。

`inflight` 是"现在在跑几个回合"，`waiting` 是"排了几个、什么优先级"——判断要不要调额度，
看这两个数就够。管理台「系统指标」页把最要紧的四个数做成了卡片：回合端到端 p95、其中排队 p95、
同时运行 / 上限、本服务内存（`SystemMetricsTab` 的「容量与延迟」一组）。

## 观测：回合延迟与排队（反 coordinated omission）

"排队不丢"有个副作用：等待时间会被算在系统之外。只统计"成功返回的请求耗时"，面板上一切
正常，而用户其实已经等了三分钟——这就是 *coordinated omission*（Gil Tene；工程版解释见
[ScyllaDB 那篇](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)）。所以这里
把两段分开记，谁也不许替谁掩盖：

| 字段 | 含义 |
|---|---|
| `rounds.latency` | 一轮的**端到端**时长（从事件被派发起，含排队）——"用户等了多久" |
| `rounds.queue` | 其中排队等名额的那一段（只有真排过队的样本） |
| `admission.waiting_ms` | 排队时长分位 `{count, p50, p95, max}`（毫秒，窗口 256 条） |
| `admission.waited_seconds` | 累计排队秒数 |
| `admission.slow_waits` | 排队超过 30 秒的次数（同时会打 warning） |

两段相减就是"实际执行"的时长；**只看 `rounds.latency` 而不看 `rounds.queue`**，会把
"系统忙"误读成"模型慢"。

诚实说明覆盖边界：`rounds` 目前只统计**会排队的地方**——群回合与群助手。私信与闹钟是在单
消费者 worker 里串行 `await` 的（天然最多一个，不经过准入），它们的耗时看
`llm.latency` / `tools.*.latency`；等它们也改成并发派发时再统一。

## 刻意不做的

- **自动改连接池大小**：PG 连接是实例级资源，动态改池要重建引擎，会漏僵尸连接；池子大小是
  部署决策，只在重启时按配置建。
- **自动提高每群并发**：一个热闹的群能吃掉全部配额，别的群和私信永远排在后面。
- **按 AI 数量线性加额度**：AI 数量与并发不是一回事（100 万个空闲 AI 只要几十 MB）。
- **基于历史曲线调阈值**：见边界 1。

## 以后的边界在哪

单进程 + 内存队列 + 进程内信号量，能优雅覆盖的是"单机可承载的并发回合"。再往上：

1. **分片**：按 `agent_id` 取模分到 N 个副本，每个副本跑一份本模块，各自读自己的额度；
2. **外部队列**：消息进入队列（Redis Stream / Kafka），副本按消费者组领取，天然背压；
3. **跨进程配额**：上游 LLM 的 key 配额、租户额度放网关或 Redis 计数，进程内只做本片
   的准入。

这三件事都不需要改业务代码里的 `slot()`——它本来就是"本进程"的语义。
