# 从聊天记录导入

> 把用户在别处（DeepSeek / ChatGPT / Claude …）与某个 AI 的对话搬进 Copree：
> **创建 AI 时多一个入口，导入的对话写进「该 AI ↔ 创建者」的私信历史**，
> 每条消息带 `via='import'`（界面上显示「来自导入」，与「来自 QQ」同一种标）。
>
> 本文只写**已经拍板**的部分。智能整理（提示词/记忆/知识库/初摘要）、
> 「默认配置兜底统一」是另外的批次，不在本文范围。

## 一、边界：为什么分三层

| 层 | 做什么 | 在哪 | 为什么在这 |
|---|---|---|---|
| **统一结构** | 一份 JSON，只描述「谁在什么时候说了什么」 | `backend/app/services/chat_import/schema.py` | 平台自己认的格式，唯一契约 |
| **解析器** | 别家的东西 → 统一结构 | `backend/app/services/chat_import/parsers/` | 纯函数，不起网络、不落库 |
| **抓取** | 给一个链接 → 拿到原始 payload | `backend/plugins/chat-import/`（插件） | **拉取各平台不合它们的规**，出问题能整个卸掉，不脏核心 |

三条铁律：

1. **核心不碰网络。** 平台服务只吃统一结构；链接解析走插件。卸载插件后导入功能的
   「粘贴 / 上传文件」两条路照常可用。
2. **解析器是内部的。** 不做「让用户选处理脚本」的交互——识别不了就退回粘贴，
   用户不该为我们的适配成本做决策。
3. **拿不到的原文件要如实说。** 附件只有元数据时标 `unavailable`，导入界面与
   会话记录里都显示「无原文件」，不假装有。

## 二、统一结构（transcript v1）

```json
{
  "version": 1,
  "origin": {
    "platform": "deepseek",
    "source_url": "https://chat.deepseek.com/share/xxxx",
    "parser": "deepseek.share",
    "parser_version": 1,
    "fetched_at": "2026-11-27T00:00:00Z"
  },
  "title": "装修方案",
  "participants": { "user": "我", "assistant": "DeepSeek" },
  "messages": [
    {
      "role": "user",
      "content": "帮我列个装修预算",
      "at": "2026-11-26T13:22:35Z",
      "attachments": [
        { "name": "照片2.jpg", "size": 1258291, "mime_type": "image/jpeg",
          "type": "image", "available": false, "reason": "no_source" }
      ]
    },
    { "role": "assistant", "content": "……", "at": null }
  ],
  "warnings": ["3 个附件没有原文件，仅保留文件名"]
}
```

约定：

- `role` 只有两个值：`user`（创建者）/ `assistant`（那个 AI）。说话人名字只用于展示。
- `at` 可空——拿不到时间就不编，界面按导入顺序显示。
- `attachments[].available` 缺省即 `true`；`false` 时带 `reason`（`no_source` / `too_large` / `fetch_failed`）。
- 解析器只**增**字段不改语义；不认的字段进 `warnings`，不静默丢。

## 三、落库

导入的对话**进历史**（用户拍板：*「导入本来就是那个 ai 的，所以某种程度上本来就是它自己」*），
写到 DM（该 AI 的 `agent.user_id` ↔ 创建者 `users.id`）的会话里：

- 每条消息 `sender_id` 按 `role` 映射；`created_at` 用原始时间（拿不到才用导入时间）。
- `via='import'`。这就是「来自导入」标签的全部来源，与 `via='qq'` 同一套机制。
- 导入的消息 **`read_at` 直接置为导入时间**：历史不该把用户的未读数顶成 99+。
- 批量落库，不走 `send_dm_message`——那条路会做表情归一、好友校验、实时推送，
  一次几千条既慢又会把会话刷成实时消息。
- 一次导入记一行 `chat_imports`（agent / session / 平台 / 来源 / 条数 / 时间），
  用于「导入期间」展示与一键撤销。

## 三之二、导入的消息与 AI 自己的上下文

导入写的是**消息**，AI 的上下文是另一套账本（`history_entries`，append-only）。
两者之间由 `sync_dm_history` 按消息 id 增量衔接（见 `services/history/context_sync.py`）：

- 下次这个 AI 在私信里说话时，水位之后新增的消息会补进账本，**一次一批（cap）**，
  超出的部分折成一条「跳过 N 条」的缺口条目，不会把整段历史硬塞进请求；
- 所以导入三千条不会撑爆上下文，而是「最近一小段进账本 + 明确标出还有更多」；
- 想要更早的内容，靠 AI 自己检索——这正是用户说的「供查阅」，不是「全部塞进去」。

这一条是既有机制的自然结果，本批次没有为导入改动任何上下文代码。

## 三之二、智能整理（提取提示词 / 记忆 / 知识库）

导入面板上的「智能整理」按钮，把这段对话提炼成**建这个人设要用的材料**。判据与创建助手
完全同源（`services/creator/agent_creator_service.py` 的 system prompt 与 `set_knowledge_docs` 说明）：

| 产出 | 去哪 | 判据 |
|---|---|---|
| `prompt` | 创建表单的系统提示词（**预填、可改**） | 它是谁 / 怎么说话 / 有哪些重大的事——身份·关系·说话方式·边界四层。**大的情景写进来**，这次聊的具体事务不写 |
| `memories` | 记忆库（rough + detail 两层） | 一句话就能记住的事实：偏好、决定、重要事件、约定 |
| `knowledge` | 知识库 | 想起来才去翻的大段资料（世界观、年表、成批示例）。多数情况为空 |
| `summary` | 上下文账本（同「三之三」） | 交代「我们之前在别处聊过什么」 |

一句话记法：**不看着它就没法开口的进 prompt；想起来再去翻的进 knowledge；一句话能记住的进 memories。**

工程上的三个决定：

1. **模型从哪来**：这是 AI 创建**之前**的事，没有「该 AI 的绑定配置」这一档，所以走
   `resolve_user_llm`（池 → 用户默认），与创建助手同一条链。用不了时**不报错**——
   回 `200 + needs_config`，前端弹统一对话框（`components/ConfigFallbackDialog`），
   带「去设置默认配置」的入口。「还没配」是下一步要做的事，不是故障。
2. **提示词只预填、不直接写死**：整理完的结果填进创建表单，用户看得见、改得动。
   替用户把提示词定死，等于替他决定这个 AI 是谁。
3. **攒一次调用**：四样由一个 JSON 输出一次拿全，不调四次——省额度，也让四个字段之间
   不打架（同一次判断里决定谁放哪）。

## 三之三、初步摘要注入

导入时除了写消息，还往该私信的**上下文账本**落一条 `kind="summary"`：

- 正文来自 `transcript.summary`：服务端先用已知事实拼一句草稿（时间 / 平台 / 条数 /
  第一句提问），前端在预览里给一个可改的输入框——**不调模型**，所以不需要任何 API 配置；
- 位置在「开场私信」之后、导入的消息之前（消息要等 AI 下次说话时 `sync_dm_history`
  才补进账本），读起来就是「先说清我们在别处聊过，细节在下面的记录里」；
- 空的摘要不落条目——不写一条没内容的占位；
- **释放是既有机制**：`rewrite_context` 是账本唯一的重写点，它只保留「摘要 + 最近 N 条
  + 事件」，这条旧摘要随之被新算出的摘要顶掉，压缩逻辑一行没改。

将来「智能整理」接上模型摘要时，只换草稿的来源，落点不动。

## 四、附件与「无原文件」

分享链接里拿不到原图（平台审核闸门），官方导出里通常有。所以：

- 能拿到 → 走既有附件通道，正常落库；
- 拿不到 → 只存 `{name, size, mime_type, type, available: false, reason}`；
- 前端在**导入预览**与**会话记录**两处都显示「无原文件」灰标，点击不打开预览。

## 五、接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/chat-import/resolve` | `{source:{type:url\|file\|text, value}}` → `{transcript, stats, warnings}`，不落库 |
| POST | `/agents/{id}/chat-import` | `{transcript}` → 写进 DM 历史，返回 `{import_id, imported, skipped}` |

`resolve` 的 `source.type=url` 需要抓取插件；未安装时回 409 并提示改用粘贴/上传。

## 六、前端

- 创建页（`/agents/create`）入口区加**两个**导入入口，与「继续上一次 / 开始新的」并列：
  - **从聊天记录导入** → 解析面板（下文三步），再进表单；
  - **从文件导入** → 灵魂档案弹窗。这就是原本只长在 AI 列表页的 `ImportSoulModal`，
    抽成 `SoulImportDialog` 后两处共用一份实现（单一来源），行为不变。
- 导入面板三步：选来源 → 预览（条数 / 平台 / 无原文件数）→ 带着这份对话去创建。
- 创建成功后自动 apply；失败不清空已解析结果，可重试。
- 「来自导入」标签：`MessageBubble` 里 `via === 'import'`，与 `via === 'qq'` 同一个位置。

## 七、明确不做（本批次）

- 智能整理里「用模型给人设润色/扩写」这类再加工 —— 目前只做一次提取。
- 「默认配置兜底统一」的**机制化**（把所有消费默认配置的地方收进一个必经入口）——
  这批只在智能整理这一处把「缺配置」的落点统一成了同一个响应形态 + 同一个弹窗；
  其余调用点还没搬过来。
- 「默认配置兜底统一」的机制化 —— 独立工程。
- 让用户选解析脚本 —— 不做，见上文铁律 2。
