## 1. 在漏斗里的位置

    外界信息 → 系统排队 → 程序决策代理 → 免打扰、屏蔽设置 → 代理 LLM → 主体状态帧

`→` 的语义：仍继续唤醒。任何一级拦下，后面都不再执行。

| 级 | 现实现 | 成本 | 拦不拦 |
|---|---|---|---|
| 系统排队 | `ai/chat_chain.py`：群并发槽、尺时间 `ruler_time`、帧排队 | 内存，0 token | 排，不拦 |
| 程序决策代理 | `services/world/decision_skill.py`：AI 自写的 when/do 规则，命中即代发或静默 | 纯代码 | 能拦 |
| 免打扰、屏蔽设置 | dnd、muted、按人静音、离线、`mention_only`、@ 本人 / @all / 群公告 / 特别关心 | 几次查库 | 能拦 |
| **代理 LLM** | 本文 | 约主体单轮的 5% | 能拦 |
| 主体状态帧 | 本尊那一轮，完整上下文 + 工具 | 30k–110k prompt | — |

旁注（原文）：**AI 自己写程序决策可以实现，只不过在平台侧；已写好，且满足相当一部分场景需要，
调用也比较简单低成本，故单列出。**

## 2. 为什么值得做

一周（2026-10-26 ~ 11-02，`ai_conversation_logs`）：

| 类型 | 轮次 | 平均 prompt | 无产出 | 其中纯发呆 |
|---|---|---|---|---|
| 群聊 | 168 | 108k | 86（51%） | 59 |
| 私聊 | 66 | 66k | 6（9%） | — |
| 闹钟 | 24 | 71k | 16（67%） | 全部调了工具 |

- 「纯发呆」＝只调了 `end_turn` / `system_reminder` / `pop_state`，什么都没干：59 轮、1.77M prompt。
- 无产出**不等于**发呆：剩下 27 轮在 `send_gm`、`bili_search_video`、`bili_comment`、`update_alarm` ——
  它干了活，只是没在群里发言。所以代理问的必须是「值不值得拉本尊进来」，不是「要不要回这句话」。

## 3. 代理 LLM 看到什么（极简上下文）

| 块 | 内容 | 说明 |
|---|---|---|
| 角色自述 | 它的角色提示词的压缩版，保持最新 | 篇幅小，能一眼看出「它在这个群是干什么的」 |
| 最近对话 | 最近 5 分钟内的对话，最多 10 条（**时间与条数取小**），单条截 200 字，去掉已在账本里的触发消息 | 只看条数会给很久以前的话，只看时间会在热闹群灌几十条；实测一整包 441 字 |
| **心情块** | 现有的心情段 | **明确要求保留，不要因为瘦身把它扔了** |
| 场景 / 交待 | 当前状态帧的交代 | 与主体帧同一来源，不另起一版 |
| 个性化规则 | 该状态帧递给它的规则（§5） | 仅在该帧拉代理时递 |
| 待判消息 | 最近几条 + 本条 | 尾巴小，见 §4 |
| **@ 到了谁** | 正文里就地注成 `<@!id>（名字）（不是你）` | 名字现算、与账本同一份；"不是你"是事实（这条路径只在没点你时被问） |

不加安全提示、不加平台说明。它只需要回答一件事。

**「@ 的是谁」必须给成一句事实，不能让模型自己比。** 代理只会在「没点名本人」时才被问到
（`decider._proxy_applies`），所以"不是你"永远成立，写出来就行。注脚就地跟在 id 后面
（`<@!120>（Deepseek 大肥鱼）（不是你）`），与账本已有的 `<@!id>（名字）` 只差最后三个字，
不另起一句话、也不新增参数：`decider._mention_annotated` 现算名字（数据源就是账本用的那一份
`message_serializer.mention_names` → `display_names`），渲染复用
`utils.text.render_mention_with_names(extra=…)`。
2026-11-14 群 77 真机：正文是 `<@!120> 那你在这里发条语音吧……`，代理判
「点名让我发语音，接我的话」并起身接话，实际 @ 的是大肥鱼；只加这三个字后，同一个模型判
「话是对别人说的，没叫我」。实测增量 **+19 字**（句尾另起一句要 +27 字）。

**不给它未读数，也不给它缺口。** 代理是逐条过的：每一条新消息要唤醒本尊，都得先经过它。
所以「窗口之前那些没看到的」对代理不是盲区——里面只要有一条值得唤醒，代理当时就已经把本尊叫醒了。
再递一句「还有 N 条没看」，等于让它复核自己已经做过的判断，既花钱，又容易把它从「判这一条」
推成「提醒本尊去补课」。

本尊不一样：它一次醒来看 20 条加一条缺口，那个缺口必须给它。**代理没有积压，因为它就是消化积压的那一层。**

## 4. 缓存：一个 AI 一个请求 id

原文：**代理 LLM 因为尾部动态变化的内容几乎无关，故而一个 AI 用一个请求 id 即可，
这样所有的（不同的）群聊触发都能命中缓存，但拼的具体的消息处理那些按每个状态帧自己来。**

- 拼装顺序按**稳定度从高到低**：角色自述、心情 → 场景、记忆 → 规则 → 本条消息。
  缓存命中的是最长公共前缀，所以换群也至少命中「角色 + 心情」那段，换帧只 miss 尾部；
  「一个 AI 一个请求 id」成立的前提就是这个顺序，顺序一颠倒整套缓存就白费。
- 尾部（具体消息）每个状态帧自己拼。
- **按相关度检索的记忆不要进这个提示**：它随每条消息变，等于把前缀整段打乱。最近对话
  （5 分钟 / 10 条）属于尾部，随消息变没关系；要放"记忆"就按解锁点冻结成一段，别逐条检索。
  这条是上面「尾部几乎无关」的直接推论。

## 4.5 判定留痕（自动停用的依据）

门卫每次判断落一行，否则 94% 无从统计、影子期也无从评估：

| 字段 | 用途 |
|---|---|
| agent_id、帧身份（type + context_ref） | 「同一帧」的统计与三次提醒计数 |
| message_id | 幂等：同一条消息不重复判 |
| wake、reason | 影子期与 enforce 期的对比、误杀采样 |
| created_at | 最近 50 次窗口 |

一行一个判断，量与消息数成正比；账本只收那句 why，明细留在这一张表里，两处不混。

## 5. 状态帧给代理递规则

- 状态帧可以给代理 LLM 递**个性化**规则；
- 平台返回投递成功（AI 知道递到了）；
- 该状态帧的主体上下文里能**看到递给代理的完整规则**——仅在此帧拉代理时递；
- 能改、能撤回。

## 6. 阈值与自动停用

样本窗口：满 10 次后开始评估，看最近 50 次。

**一个旋钮，不是两个。** 94% 和 6% 是同一个数的两面：唤醒率 94% ⇔ 拦下率 6%。
配置只存一个 `min_saving_ratio`（默认 0.06），另一个由它推出来，不单独落值——
两个独立可配的数迟早会被改成「94% + 7%」这种自相矛盾的状态。

| 条件 | 结论 |
|---|---|
| 唤醒率 > 94%（即拦下率 < 6%） | 之后不再经由代理 LLM，直接放行 |
| 拦下率 ≥ 6% | 继续经由代理 LLM |

成本口径（原注）：**代理 LLM 的 token 消费约略低于主体的 5%**，所以门槛就压在 5–6% 这附近。

这一条是**成本兜底**，不是学习机制：它只回答「还值不值得经代理」，不负责让代理越用越聪明。
判定样本沉淀成规则是另一件事，当前不做。

三个值都是配置项、不是常量（线值要改只改配置）：

| 配置 | 默认 | 含义 |
|---|---|---|
| `PROXY_MIN_SAVING_RATIO` | 0.06 | 拦下率下限，低于它停用代理 |
| `PROXY_SAMPLE_MIN` | 10 | 满多少次才开始评估 |
| `PROXY_SAMPLE_WINDOW` | 50 | 评估看最近多少次 |

## 7. 三次提醒

口径：**同一状态帧、同一段上下文内，被消息触发超过 3 次**，就劝它一次（阈值可配）。
「一段上下文」= 帧的生命期：解锁（compact / clear）即复位，新的一段上下文不知道这件事，再劝一次是合理的。

**机制：往账本投一条条目**（`services/brain/frame_reminder.py`）。

| 要件 | 取值 | 为什么 |
|---|---|---|
| 投递 | `history_service.append` 一条 `kind=note` | 账本是 AI 一定看得到的地方，也已经是计划板、记忆便签的投递通道 |
| 幂等键 | 条目 `ref = remind:over_woken:<日期>` | 同一天同一个群只劝一次 |
| 复位 | `flags={"drop_on_unlock": True}` | 投递过的条目在解锁时离场，新的一段上下文可以再劝一次 |

**不能拿帧上的 `delivered` 做幂等**：群帧一轮一换（聊完就 end，下一轮是新帧实例），
状态随帧生灭。2026-11-02 实测：agent 57 在群 83 连着六轮各投了一次——每一轮都是新帧，
`delivered` 每一轮都是空的。`delivered` 适合「工具触发的规则」（同一帧内可能多次触发），
不适合跨轮的消息级提醒。这也是本节与 §4「缓存」无关的一个副产品：记忆/提醒这类
**跨轮**的投递，幂等键必须落在账本或表上，不能落在帧上。

**出口：上下文本身就是出口。** 同一段上下文只劝一次；它要是不改，下一段上下文再劝一次——
因为下一段上下文确实不知道。不另设「劝两次就闭嘴」或「升级给主人」：那要额外的计数与状态，
而投递制已经把重复压到「每段上下文一次」，再加一层等于给同一个目的写两套机制。

- 提醒递进主体帧：建议用屏蔽、免打扰，或写一条自制策略，以免被无需回复的消息反复唤醒；
- 平台只提醒，不替它设；它自写的策略不能把一切都挡掉（设定的勿扰时段除外）。
- 一条要认的瑕疵（不改）：`tool_uses` 在判定 `delivered` **之前**就 +1 并落库，
  `first_in_frame` 的窗口很窄。它回答的是「这个工具第几次被调用」，不是「投过没投过」——
  两个事实分开是对的，改动它会波及 `web_search` 那条已有规则。本节按 `delivered` 判幂等，
  不依赖那个计数，所以绕开它，而不是改它。

提醒指的都是**已有工具**，这条机制不需要新能力，只是现在没人告诉它「你可以这么做」：
`set_dnd`（整群勿扰，@ 仍穿透）、`mute_group`（≤30 分钟，连 @ 也不穿透）、
`silence_member`（按人静音，连 @ 也不唤醒）、`update_ruler_time`（放慢自己的尺时间）、
决策代理的 `silent` 规则（自制策略）。

## 8. 失败、超时、开关、灰度

- 超时 2s 或报错 → 退回现有的 `calc_reply_willingness` 启发式；不 fail-open 拉本尊，也不 fail-closed 让 @ 失声（@ 在前置已放行）。
- 影子模式：先只判不拦，记「正确拦截 / 误杀」两个数，一周后再开 enforce。
- 留白：`PROXY_WAKE_ENFORCE=1` 打开后，`PROXY_WAKE_SHADOW_GROUPS=66,81` 里的群继续只判不改，
  其余群按判定执行。要放量某个氛围群，把它的群号从名单里删掉；回滚就是关总开关。
  名单只管群：没有群号的判定（私信、闹钟）不走这道门。
- 开关：群级 / 世界级；默认只在 `group_trigger_mode=all` 的群开（`mention_only` 群里开它纯是开销）。
- 群规与公告：群主/管理员在群设置里写「AI 决策代理规矩」（空 = 默认口径），并勾选
  「允许 AI 的决策代理看本群公告」（默认开）。代理上下文按 场景 → 群主规矩 → 群公告 →
  AI 自己记的规矩 → 角色 → 心情 → 对话 拼接；群规靠前，同一群的判定命中同一段前缀。

## 9. 它替换掉什么

现状 `ai/decider.py` Gate 4/5，即 `utils/pure/willingness.py` 的纯字符串启发式：
底分 50、被 @ +40、含 `@ai`/`@all` +20、短消息 −5、长消息 +10，低于 `auto_dnd_threshold`（默认 20）不回。
它数了长度、查了 @，**读不懂那句话在说什么**。本层只替换 Gate 4/5，前置 Gate 0–3 原样不动。

## 11. 将来的验收

- 影子期两个指标：代理说不用而本尊确实只 `end_turn` 的次数（正确拦截）、
  代理说不用而本尊干了活或发了言的次数（误杀率）；
- 灰度期按群看这两个数：误杀集中在哪个群，就先别给那个群放量；
- **判定不符合群时，先改群规、别调阈值**：代理上下文里已经带「这个群的规矩（你自己定过）」
  （帧上的 `proxy_rules`），把「这是角色扮演闲聊群，气氛话、表情、晚安也该接」
  「别人之间的问答不插话」写进去，判定就会按这个群自己的标准走，而不是全局一个口径。
  目前该字段能进提示但还没有写入路径——给它一条口（AI 自己的工具或后台），
  再拿误杀样本往回标，规则就是这么长出来的；这正是本文开头「把判定样本沉淀成规则」那条没做完的事；
- 自动停用按单一旋钮算（`min_saving_ratio`），样本达标后生效且重启不丢；改配置只改环境变量；
- 同一 AI 不同群的触发共享前缀缓存（看 `cached_tokens` 占比）；
- 三次提醒：同一段上下文只投一次、解锁后能再投一次；提醒里点的工具它真能用；
- 判定留痕表一行一个判断，同一条消息不会出现两行。

## 12. 待办：群级智能开关（未实现）

群可以选择是否启用「智能开关模式」，由灰度数据自己决定要不要在本群 enforce。用户给的口径是
**示例值（"如"）**，不是契约数字——群的样本量与被唤醒频率差得远，别把它写死成全局常量：

- 先看前 20 条**左右**的灰度判定：误判率小于**约** 40% 就启用本群 enforce；
- 达不到，再看最近 50 条**左右**：误判率小于**约** 35% 才启用；
- 两条都不满足就继续影子，不启用。

（40% / 35% / 20 / 50 都是"如"的量级，实现时按群可配、有默认值，不要在代码里写死。）

实现前先把「误判率」的口径钉死（分母是灰度判定条数还是落轮次数、误判怎么从
`proxy_judgements` 与发言记录里判出来），并落成纯函数 + 用例，再谈自动开关。
这条是产品待办，本轮不实现。
