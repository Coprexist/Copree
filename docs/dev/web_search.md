# web_search（多后端并发检索）

工具壳在 backend/app/tools/file_operations/web_search.py，编排在同目录 search/ 包；
世界侧 tools/world/web_search.py 复用同一份文案与参数（唯一来源）。

## 1. 为什么不是「一条原话丢给引擎」

搜索引擎对查不到的冷门词**不返回空集**，而是塞一批无关结果。实测（本机容器）：

| 查询 | 直接丢进去的返回 |
|------|--------------|
| Copree AIsChat | 外设驱动站 / 视频站 / 黑龙江人社平台（每次还不一样） |
| Copree（AIsChat）类似平台的发展和发布 | 留学中介、知乎录取率帖 |
| 数字生命 AI 群聊 项目 开源 | 阿拉伯数字书写规范、数字转大写工具（线上真机：10 条全过闸） |
| 赛博生命 CyberLife 数字生命 AI 社区 项目 | 10 条全被丢掉 → 返回「没有与该实体字面相关的公开结果」（线上真机） |

旧实现把这些原样当成功结果端给模型，于是「搜不到」表现为两种样子：**全是导航站和工具页**，
或者一句「没找到」。所以相关性判定是**硬闸门**，不是排序里的一项权重；
而闸门的判据必须分语言——上面两行的失败原因正好相反（一个太松、一个太紧）。

## 2. 契约

web_search(queries=[...], exclude=[...], count=8, per_domain=3)

- queries：1~4 条检索式并行；单条写法 query 保留兼容
- exclude：负向词，既拼进引擎查询（-term）又对标题/摘要后置过滤
- count：结果上限（<=10，默认 8）
- per_domain：同一域名上限（<=5，默认 3）——不让一个站刷满整页

返回 {success, queries, provider_used, count, results[], attempts[], failed?[], hint?}；
results[] 每项含 title/url/snippet/published_at/domain/provider/**engines**/score/authority/matched_query。
attempts[] 每项 {provider, query, parsed, kept, error?}——**「搜不到」时先看它**：
是引擎解析为 0 / 超时 / 没等它，还是解析到了全被闸门拦下。

hint 只在 0 条时给，写事实不写猜测：哪几家引擎、一共取回几条、
是引擎这一轮没给东西、还是检索式里没有可判定的实体词、还是取回的内容没命中实体——
再给出下一步（向用户索要链接 / 换中文说法或英文通用词再搜）。
这段文字会被模型转述给用户（实测它把这里的话说成「搜索引擎自己都标了」），所以不能含糊。

authority 是域名先验权重（官网 1.0、官方发布页 0.9、GitHub 0.85、科技媒体 0.7、聚合导航 0.1）。
平台只给先验，不给"这是不是官网"的结论：同一实体的官方页形态各异（自有域名 / 平台仓库 / 镜像），
硬编码判定必然出错。

建议的做法：先及时把搜到的回复对方，再用 web_fetch 点进去核对版本号与发布时间这类会变的信息，
有出入再补充或更正。核实要花时间，别让对方干等；但这是建议不是死规矩，节奏由模型自己权衡。

## 3. 并发、超时与回退

**一轮 = 所有后端并发**（orchestrator.`_fan_out`）。串行阶梯下总时长是各引擎之和，
实测最快也要 3~5 秒、引擎挂住时能把一个对话轮次拖到二十秒；而它们的失败彼此独立，
并发后总时长等于最慢的那家。

- **轮转铺开**：`_allocate` 把检索式轮流分给各后端，每家最多 2 条（`PER_BACKEND`）。
  这样每条检索式至少被两家引擎搜过（共识信号在），请求数又只有「每家都跑全部」的一半。
- **两段等**：先等到 `SOFT_DEADLINE`（5 秒）。这段结束时**只要手上已有过闸的结果就不再等剩下的引擎**
  ——并发是为了快，等齐慢的那家只会把延迟拖到它的水平；一条都没过闸才等到 `DEADLINE`（8 秒）。
  没等到的记 `没等它`，等到超时的记 `超时`，两者在实况里分得开。
- **单请求超时 4 秒**：引擎正常 0.5~1.5 秒，挂到四秒就是抽风，让它在本轮内重试一次
  （同一请求前后几秒结果不同是实测过的，重试比换引擎便宜），好过拖到回退轮。
- **回退按原因分岔**（这是踩出来的：判据含糊时回退只是在烧请求）：

  | 上一轮的样子 | 说明 | 回退动作 |
  |---|---|---|
  | parsed=0 / 超时 | 引擎自己没给东西 | 让**那几家**重跑同一批检索式 |
  | parsed>0、全被闸门拦下 | 检索式本身不对 | 换**机械改写补出的候选**（去标点、拆粘连词、单拉丁词元） |

- 上限：单次调用对外请求 <=12（`MAX_REQUESTS`），时间用尽的那一轮直接不发请求。

语言层面的规划（挑哪个实体、要不要英文说法）仍留给调用方模型：它本来就在场，
工具内部再调一次模型只会多一次往返和一份 token。但**工具描述里给了面向语料的写法**
（专名照抄、中文说法 + 英文说法各一条、短语加引号、找开源项目带 github / site:github.com），
因为线上实测的短板正是这一环：模型把整句原话丢进来，或自己音译一个外文名当检索式。

## 4. 后端表

search/backends.py，顺序即优先（并发后它决定轮转的起点，不再是「前一家没有才轮到下一家」），
只登记实测过的：

| 后端 | 状态 |
|------|------|
| 必应（RSS 出口） | 唯一能搜到 AIsChat 的后端（掘金 / GitHub Coprexist / CSDN / gitcode 全部命中）；约 4KB 结构化 XML，字段齐全且无广告位 |
| 必应（网页出口） | 与 RSS 同源、结果不同批；冷门词会被塞无关填充，由闸门拦掉 |
| 360 搜索 | 结果真实地址在 a[data-mdurl]（页面 href 是跳转链）；**中文长查询上常比必应准**——线上那两条「搜不到」的查询，真结果都是它给的 |
| 搜狗 | 真实地址在 a 的 linkurl 属性；实测多半返回 0 条 |
| DuckDuckGo | 本机网络不可达（Errno 101），不登记 |

**必应会间歇性空手**：同一个 URL、同一份代码，一次返回 8 条正确结果、几分钟后整轮拿不到东西
（实测踩过，表现为静默落到 360，于是「平台搜不到、浏览器搜得到」）。

要接需要密钥的搜索 API（Tavily / Serper 之类）在这张表里加一行即可，契约与排序都不用动。

## 5. 闸门、融合与排序

**闸门**（rank.relevant）按语言分档：

- 查询里有中文：看**非泛词汉字块**（`content_blocks`）。整块出现最理想；长块允许一半以上二元组命中
  （调用方常把半句话当检索式，整串判会把它们全毙掉）。
  - 按单个二元组判会放水：「数字生命」里的「数字」命中就放行，于是阿拉伯数字书写规范过闸。
    泛词表（`_GENERIC_BIGRAMS`）因此补到 40 多个词，全是实测踩过的假阳性来源。
  - 一块都判不动（「项目 开源 平台」）就是全否，并在 hint 里说明是检索式的问题。
- **中英混排时拉丁词只加分不否决**：模型顺手音译的外文名（CyberLife）不该把真正的中文结果毙掉
  ——线上就是这条把 10 条全丢了，然后返回「没找到」。中文侧全是泛词时（「AstrBot 项目 开源」）
  实体词照旧要求全部命中。
- 纯拉丁查询：实体词**全部**命中（AIs 会命中 AIS 船舶系统）；机械拆词派生的候选还要相邻命中。
- 引号里的中文短语整串必须出现，且它本身就是判据（调用方写引号就是要精确匹配）。
  拉丁引号短语不做逐字校验：引擎侧已按短语处理，本地再校验会把分词、单复数这类宽松匹配全误杀。

**多引擎融合**（rank.fuse_engines）：同一 URL 被多家引擎给出时并成一条，`engines` 记下都有谁给过。

- 用「几家引擎都挑中同一个 URL」当共识信号：单家引擎的前 10 名只是一次抽样，
  两家独立引擎同时给出比任何单一权重都可靠。
- 不做 RRF 的倒数排名累加：每个引擎只取 10 条、名次本身就是抽样噪声，
  有界的共识加分（每多一家 +0.12，最多 +0.24）更稳。取舍的来由见 §6。

**打分**：实体命中 0.55 + 域名权威 0.30 + 新近 0.15 + 共识加分。实体仍占大头——先看是不是它，再看站可不可信。
去重：URL 归一 -> 标题归一 -> 内容 simhash（64 位；摘要 >=30 字才用正文指纹）。
加工顺序：融合 -> 去重 -> 打分 -> 每域名限量 -> 截断。

## 6. 参考实现对照（读过源码之后的取舍）

| 参考 | 它的做法 | 我们怎么处置 |
|------|----------|--------------|
| nexus-rs（Rust 多引擎 + RRF） | `RRF_K=60`，`rrf=1/(60+rank)` 相加；候选未参与某一路时按最差名次计入；同 URL 被 >=2 源确认则乘 `consensus_multiplier` | **分歧**：只保留「多源确认」这个想法，做成有界加分。每个引擎只取 10 条，`1/(60+rank)` 在这 10 条之间的差异小到淹不过域名的先验差异，不如让共识直接可解释 |
| SAC_search（DeepSeek 插件形态） | `relevance = max(词项命中率, 字符覆盖率×0.75)`；乘法软闸 `score *= 0.02 + 0.98*rel`，无关页压到 2% 而不是丢掉 | **分歧**：保持硬闸门——结果直接端给模型，「2% 相关」的页面会被当成答案。**采纳**它的另一半：相关性不该被一个猜的英文词一票否决 → 用「混排时拉丁词只加分」实现 |
| web-search-mcp（免 Key 多引擎 MCP） | `score = 1.0×RRF + authoritySignals`；权威域豁免覆盖率硬过滤 | **采纳**「权威与融合相加、互不覆盖」：我们的 authority 本来就只进排序、不进闸门 |
| Anthropic search-strategy skill | 先分类（decision / status / factual / temporal…）再抽槽位；**每源一条查询**并行；查询写法（2~5 个核心词、引号短语、`site_search(domain, query)`、别名扩写）；回退顺序：去日期 → 去来源 → 少见词 → 只留核心实体 | **采纳**进工具描述（面向语料的写法）与 §3 的轮转铺开；回退顺序里「去日期 / 只留核心实体」还没做，见 §8 |
| ManuSearch / HiRA（显式规划智能体） | Planner 迭代出子问题（ReAct + memory），每次搜索 <=3 条子查询、每查询 top-5 | **不做**：那要工具内部再挂一个模型（多一次往返、一份 token）。规划留在调用方模型，工具只负责把实况告诉它 |
| SAC_search 的时效 | `score *= max(0.75, 1 - days/365*0.25)`，注释写明「只做微调不改主序」 | 同口径：我们按日期分档（1.0 / 0.8 / 0.6 / 0.4），也不让时间翻过主序 |

## 7. 刻意不做

- **不猜域名**（copree.ai / copree.com ...）：猜出来的域名与我们无关，会撞上别人的站，
  还会让模型以为那是官网。
- **不自动抓 sitemap / blog / changelog**：那是 web_fetch 的职责；工具只给建议，
  避免一次搜索偷偷拉二十个页面。
- **不替调用方翻译**：把英文说法直接放进 queries，比在工具里再调一次模型便宜。
- **不做乘法软闸**：见 §6 第二行。

## 8. 已知残留

- **聚合站把整条检索式原样回显**（360 的短视频站 / 图片站，标题就是查询词加个尾巴）：
  字面判据认不出它——它确实"包含"查询里的每个词。现在只能靠 authority 0.1 让模型自己掂量。
- **`_norm_url` 保留 query**：`?utm_source=` 这类同一页面的不同地址不会被融成一条、也不判重。
- **回退只剩机械改写**：Anthropic 那份回退顺序里的「去日期 / 去修饰词 / 只留核心实体」还没做，
  现在能补的候选是去标点、拆粘连词、单拉丁词元。
