# 兑换码系统 / Redemption Code System

> 本文档描述 Copree 的兑换码体系：四种额度类型、生成与兑换流程、API Key 池集成、额度消耗机制与安全设计。
> This document describes the redemption code system: four quota types, generation & redemption flow, API Key pool integration, credit consumption mechanism, and security design.

---

## 1. 架构总览 / Architecture Overview

```mermaid
flowchart TD
    subgraph Admin["🛡️ 管理员 / Admin"]
        GC["生成兑换码<br/>Generate Code"]
        AP["API Key 池管理<br/>Pool Management"]
    end

    subgraph User["👤 用户 / User"]
        RC["输入兑换码<br/>Redeem Code"]
        USE["使用 AI 聊天<br/>Use AI Chat"]
    end

    subgraph System["⚙️ 系统 / System"]
        VAL["验证兑换码<br/>Validate Code"]
        CREDIT["api_credit 入账<br/>Credit Accrual"]
        RESOLVE["四层 Key 解析<br/>4-Tier Key Resolution"]
        DEDUCT["扣除额度<br/>Deduct Credit"]
        LOG["api_usage_log<br/>审计日志"]
    end

    GC -->|"RC-xxxxxxxxxxxxxxxx"| VAL
    RC --> VAL
    VAL -->|"有效 / Valid"| CREDIT
    USE --> RESOLVE
    RESOLVE -->|"Tier 2/3: 池 Key"| DEDUCT
    DEDUCT --> LOG
```

**关键设计**：兑换码的「一次性能兑几次」由 `usage_limit` 决定——`1` 是一次性凭证（默认），
留空（NULL）是**限时活动码**：有效期内不限人次，但**每个人只能兑一次**。格式统一为 `RC-` + 16 位 hex，
四种额度类型覆盖不同的资源维度；已兑人次与「本人兑过没有」记在 `redemption_records` 流水表里，
两种码因此走同一条判断，不需要两套分支。

v0.1.5 引入 API Key 池后，通用 API 额度（`api_credit`）与池 Key 深度集成——用户无需自备 API Key 也能使用 AI，消耗自动从额度中扣除。

## 2. 额度类型 / Quota Types

| 类型 | 兑换码 type | users 表字段 | 说明 |
|------|-----------|-------------|------|
| **AI 创建额度** | `ai_quota` | `ai_quota` | 每创建 1 个 AI 消耗 1 点。注册默认赠送 3 点 |
| **通用 API 额度** | `api_credit` | `api_credit` | 1 余额 = 10,000 token（pay-as-you-go）。使用池 Key 时自动扣除 |
| **AI 包断额度** | `agent_bundle` | `agent_bundle_credit` | 创建 AI 时一次性支付，该 AI 后续 API 调用全免 |
| **文件存储配额** | `file_quota` | `file_quota_mb` | 单位 MB，控制文件上传空间上限 |

---

## 3. 兑换码格式 / Code Format

```
RC-A1B2C3D4E5F67890
││ │              │
││ └── 16 位 hex 大写 ── 随机生成，全局唯一
│└── 连接符
└── 固定前缀，便于识别
```

- **前缀**：`RC-`（Redemption Code）
- **随机部分**：16 位十六进制大写（`secrets.token_hex(8).upper()`），碰撞概率 ≈ 2^-64
- **存储**：`redemption_codes` 表，`code` 列有 UNIQUE 约束

## 4. 管理员生成 / Admin Generation

### 4.1 操作位置

管理面板 → **兑换码** Tab → 点击「生成兑换码」

### 4.2 表单字段

| 字段 | 必填 | 说明 |
|------|------|------|
| **额度类型** | ✅ | 四选一：AI 创建 / 通用 API / AI 包断 / 文件配额 |
| **额度** | ✅ | 一次兑换发多少：文件配额按 MB（上限 1024），其余上限 100 |
| **有效期（天）** | ✅ | 1–365 天，到期即不可兑，列表显示「已过期」 |
| **可兑换人次** | 选填 | 留空 = 不限人次（活动码，每人仍限一次）；1 = 一次性（默认）；N = 前 N 名 |
| **备注**（v0.1.5） | 选填 | 仅管理员可见，用于标记用途（如"张三充值 10 元"） |
| **单码最大用量**（v0.1.5） | 选填 | 写入 `max_usage` 列，供按额度核销的接入方使用 |
| **API 池额度**（v0.1.5） | 开关 | 标记此码为 API 池专用额度，兑换后需配合池 Key 使用 |

### 4.3 生成逻辑

生成、核销、查询都收在 `app/services/infrastructure/redemption_service.py`：路由只管取参与翻译错误码。

```python
async def create_code(db, *, admin_id, quota_amount, code_type, expires_in_days,
                     note=None, usage_limit=1, max_usage=None, is_api_pool=False):
    code_obj = RedemptionCode(
        code="RC-" + secrets.token_hex(8).upper(),
        quota_amount=quota_amount,
        code_type=canonical_type(code_type),      # file_size → file_quota
        expires_at=_now() + timedelta(days=expires_in_days),
        created_by=admin_id,
        note=note,
        usage_limit=usage_limit,                  # None = 不限人次
        max_usage=max_usage,
        is_api_pool=is_api_pool,
    )
    db.add(code_obj)
    await db.flush()
    return code_obj
```

- 管理员可在列表页看到所有兑换码，**备注字段仅管理员可见**
- 列表显示：code、类型、额度、备注（换行完整显示）、**已兑人次 / 上限**（`0 / ∞` 表示不限人次）、
  到期时间、状态（`可用` / `已兑完` / `已过期` 三态由后端算）、API 池标记（琥珀色「池」徽章）
- 点「已兑」的人数可展开**兑换记录**（谁、什么时候、兑到多少），接口 `GET /admin/redemption-codes/{code}/redemptions`
- AI 创建额度兑换后**不返还**（防滥用）

## 5. 用户兑换 / User Redemption

### 5.1 操作位置

底部导航「**我的**」→ 兑换码输入框 → 点击「兑换」

### 5.2 兑换流程

```mermaid
flowchart TD
    A[输入兑换码] --> B{格式校验}
    B -->|"不以 RC- 开头"| ERR[提示格式错误]
    B -->|"通过"| C["按码查行并加行锁<br/>SELECT ... FOR UPDATE"]
    C -->|"不存在"| ERR2[兑换码无效]
    C -->|"存在"| D{本人兑过没有}
    D -->|"兑过"| ERR5[您已兑换过此码 409]
    D -->|"没兑过"| E{是否已过期}
    E -->|"已过期"| ERR3[兑换码已过期]
    E -->|"有效"| F{已兑人次是否到上限}
    F -->|"到上限"| ERR4[兑换码已被使用 / 已兑完]
    F -->|"还有名额"| G[增加用户对应额度]
    G --> H[写 redemption_records 流水]
    H --> SUCCESS[返回成功 + 余额变化]
```

三条规则只有一份实现（`redemption_service.redeem`）：**过期 → 本人已兑过 → 名额**。
「数一数够不够」与「写流水」在同一事务里，同时抢最后一个人次的后到者会被行锁挡住；
同一个人两个请求撞在一起时，`(code, user_id)` 唯一约束再兜一层（回滚、返回 409）。

### 5.3 前后端交互

**请求**：`POST /user/redeem`
```json
{ "code": "RC-A1B2C3D4E5F67890" }
```

**响应**（成功时回四个余额，前端按需取用）：
```json
{
  "message": "兑换成功，获得 10 通用 API 额度",
  "ai_quota": 3,
  "api_credit": 15,
  "agent_bundle_credit": 0,
  "file_quota_mb": 100
}
```

**失败**（`detail` 直接用作用户提示）：

| 情况 | HTTP | detail |
|------|------|--------|
| 码不存在 | 404 | 兑换码无效 |
| 本人已兑过 | 409 | 您已兑换过此码 |
| 已过期 | 400 | 兑换码已过期 |
| 一次性码已被用掉 | 400 | 兑换码已被使用 |
| 多人码名额用完 | 400 | 兑换码已兑完 |

### 5.4 数据模型

| 表 | 作用 | 关键列 |
|----|------|--------|
| `redemption_codes` | 码的**定义** | `usage_limit`（NULL=不限人次、1=一次性、N=前 N 名）、`expires_at`、`quota_amount`、`code_type` |
| `redemption_records` | 兑换**流水**（已兑人次与「每人一次」的唯一真相） | `code` + `user_id` 唯一、`quota_amount`/`code_type`（发放快照）、`redeemed_at` |

- `used_by` / `used_at` 是 v0.1.5 的单人字段，迁移 `0100` 已把存量回填成流水；
  新代码只读写流水，这两列保留纯粹是为了回滚到旧版本时数据还在。
- 状态（`expired` / `exhausted` / `available`）由后端 `code_state()` 统一算，前端只上色——
  过期判断不该由每个调用方各写一遍（2026-11-01 就是因为列表只看 `used_by`，8 月过期的码还显示「可用」）。

## 6. API Key 池集成 / Pool Integration（v0.1.5）

### 6.1 为什么需要池

v0.1.5 之前，用户如果没有配置自己的 API Key，即使有 `api_credit` 也无法使用 AI。池 Key 填补了这个缺口——管理员可预先在池中添加共享 API Key，用户兑换 `api_credit` 后自动从池中分配。

### 6.2 池 Key 管理

管理面板 → **API 库** Tab：

| 操作 | 说明 |
|------|------|
| **添加** | 输入名称、API Base URL、API Key（密码框）、优先级 |
| **编辑** | 修改名称、启用/禁用、优先级 |
| **删除** | 移除池 Key。已绑定此 Key 的用户下次调用时自动切换到其他可用 Key |
| **列表** | 名称、URL、脱敏 Key（`****后四位`）、优先级、状态开关 |

### 6.3 安全设计

- 池 Key 使用 **Fernet 对称加密**（与用户自有 Key 相同的加密方案）
- 管理员添加 Key 时输入一次明文，保存后**仅存储密文**
- 列表展示格式：`****a3f2`（仅密文后四位）
- 管理员**无法查看已存储 Key 的明文**
- 加密密钥来自 `ENCRYPTION_KEY` 环境变量（默认复用 `JWT_SECRET_KEY`）

### 6.4 用户绑定缓存

每个用户与池 Key 的绑定关系存储在 `user_api_assignments` 表：

| 字段 | 说明 |
|------|------|
| `user_id` | UNIQUE，每用户仅绑定一个池 Key |
| `pool_key_id` | 指向 `api_key_pool.id` |
| `assigned_at` | 首次分配时间 |
| `last_used_at` | 最近一次使用时间 |

**优势**：用户下次请求时直接查绑定表（O(1)），无需每次遍历全池选 Key。绑定 Key 失效（被禁用/删除）时自动重新分配。

## 7. 额度消耗 / Credit Consumption（v0.1.5）

### 7.1 四层 Key 解析优先链

```
Tier 1: Agent 自有 Key         → 不扣额度（Agent 自己承担）
Tier 2: 用户绑定池 Key（缓存）  → 扣 api_credit（命中缓存，最快）
Tier 3: 自动选最优池 Key       → 扣 api_credit（首次或缓存失效）
Tier 4: 用户自有 Key           → 不扣额度（用户自己承担）
```

### 7.2 消耗规则

| 规则 | 值 | 说明 |
|------|-----|------|
| 兑换比例 | 1 credit = 10,000 tokens | 可通过 `CREDIT_PER_TOKENS` 环境变量调整 |
| 最低扣除 | 0.01 credit / 次 | 防零成本调用 |
| 扣除时机 | LLM 调用结束后 | `_tool_call_loop` 出口处，不阻塞主流程 |
| 并发保护 | `SELECT FOR UPDATE` | 防止并发扣除导致额度超用 |
| 审计日志 | `api_usage_log` 表 | 记录每次扣款的 user_id/agent_id/pool_key_id/tokens/credit/model |

### 7.3 用户端展示

用户可在「**我的**」页面查看：
- **通用额度卡片**：余额 + 估算 Token 数（`api_credit × 10000`）+ 绑定的池 Key 名称
- **侧边栏**：显示「额度 · 余额」双数字

## 10. 安全注意事项 / Security Notes

1. **备注保密**：`note` 字段仅管理员在管理面板可见，不会通过任何用户端 API 泄露
2. **Key 加密**：池 Key 和用户自有 Key 均使用 Fernet 加密，密钥不在数据库中
3. **一次一用**：兑换码使用后立即标记 `used_by` + `used_at`，不可重复使用
4. **AI 创建不返还**：`ai_quota` 类型兑换码创建 AI 后不返还，防止恶意刷码
5. **并发防护**：`deduct_credit()` 使用 `SELECT FOR UPDATE` 行锁，防止并发扣除导致额度超用
6. **额度扣除不阻塞**：LLM 调用出口处的 `deduct_credit` 失败时仅记录 warning，不影响消息发送
